# task2-06 — первый CLI-агент с инструментами

Интерактивный чат-агент на Go. Пользователь пишет запрос в консоль, агент
отправляет его в LLM, сам решает, какой инструмент вызвать, получает результат
и формулирует финальный ответ. Цикл повторяется, пока модель не перестанет
запрашивать инструменты.

Базовая реализация выросла из `task1-05`: оттуда взяты HTTP-клиент
OpenAI-совместимого API, работа с `usage` и список задач `tasks.txt`.
Финальный отчёт-бенчмарк (`report.go`) в агенте не используется — вместо него
консольный чат.

## Запуск

```bash
export LLM_BASE_URL="https://..."
export OPENAI_API_KEY="..."

./run.sh                 # интерактивный чат
./run.sh -script checks.txt   # три проверки из задания
./task2-06 -list-models
./task2-06 -list-sessions
./task2-06 -continue     # продолжить последнюю сессию
./task2-06 -print-session 20261111-204115-1820   # весь лог сессии, офлайн
./task2-06 -print-session last                   # то же для последней
```

`-print-session` читает только `session.jsonl` с диска: ни сети, ни ключей,
ни модели не нужно. Печатает хронологически все сообщения полным текстом,
вызовы инструментов (`→ calc(...)`, `← calc: 4`), события сжатия и смены
моделей; в заголовке — модели, с которыми сессия закончила.

Флаги: `-model`, `-summary-model`, `-session`, `-continue`, `-data`,
`-max-steps`, `-max-prompt-tokens`, `-reserve-output`, `-min-tail-tokens`,
`-max-tool-chars`, `-temperature`, `-max-tokens`, `-system`, `-script`,
`-print-session`.
Модели по умолчанию берутся из `LLM_MODEL` / `LLM_SUMMARY_MODEL`.
`run.sh` сам подхватывает `~/.env`, если переменные не экспортированы.

## Инструменты

| Инструмент | Аргументы | Что делает |
|---|---|---|
| `now` | — | текущее время (локальное и UTC) |
| `calc` | `{"expr": "..."}` | арифметика `+ - * /` и скобки, без `eval` |
| `find_task` | `{"query": "..."}` (пусто — список всех) | поиск по `tasks.txt` из дня 5 |

Схемы инструментов отправляются в запросе в поле `tools` (JSON Schema), модель
сама выбирает имя и аргументы. `tool_choice: "auto"`, `parallel_tool_calls` не
используется — шаги идут последовательно, чтобы результат одного инструмента
мог стать аргументом следующего.

## Цикл агента

```
user → LLM → tool_calls → выполнение → role:"tool" → LLM → ... → финальный текст
```

`agent.go` хранит `assistant`-сообщение с `tool_calls` дословно (включая `id`) и
добавляет на каждый вызов по сообщению `role:"tool"` с тем же `tool_call_id`.
Ошибки инструментов и паники не роняют цикл: они возвращаются модели текстом,
чтобы она могла исправить аргументы. Защита от зацикливания — `-max-steps`.

## Модели

Список моделей из `task1-05` (`config.go`):

| Модель | Тип | $/1M |
|---|---|---|
| `deepseek-v4.1-flash` | маленькая | 0.311270 |
| `glm-5.3-flash` | средняя | 0.788471 |
| `qwen3.8-27b` | флагман | 0.303003 |

Две роли:

- **чат-модель** — `-model`, команда `/model` или переменная `LLM_MODEL`;
  по умолчанию берётся `LLM_MODEL` из окружения, иначе `deepseek-v4.1-flash`;
- **модель сжатия** — `-summary-model` или `LLM_SUMMARY_MODEL`, по умолчанию
  самая дешёвая в списке (`qwen3.8-27b`). Сжатие вызывается редко и должно
  стоить меньше, чем экономит; если модель сжатия недоступна, сообщения
  всё равно архивируются, а в конспект пишется пометка.

Провайдер может отдавать не все id из списка (часть моделей способна
«повиснуть» на конкретном эндпоинте), поэтому рабочую модель удобно задать
через `LLM_MODEL`. Лимит ответа ограничен `-max-tokens` (по умолчанию 4096):
reasoning-модели тратят его сначала на скрытые рассуждения.

Смена чат-модели пишется в лог событием `model_switch`, поэтому при
продолжении сессии видно, чем отвечали.

## История: append-only JSONL

Одна сессия — один каталог и один файл:

```
$XDG_DATA_HOME/goagent/sessions/<session-id>/session.jsonl
```

Формат — event sourcing, одна JSON-запись на строку:

```jsonl
{"type":"session","v":1,"id":"20261110-233246-ab12","chat_model":"deepseek-v4.1-flash","summary_model":"deepseek-v4.1-flash","system":"...","created":"..."}
{"type":"message","message":{"seq":1,"role":"user","content":"Который час?","ts":"...","tokens_est":8}}
{"type":"message","message":{"seq":2,"role":"assistant","content":"","tool_calls":[{"id":"c1","type":"function","function":{"name":"now","arguments":"{}"}}],"ts":"..."}}
{"type":"message","message":{"seq":3,"role":"tool","content":"...","tool_call_id":"c1","name":"now","ts":"..."}}
{"type":"message","message":{"seq":4,"role":"assistant","content":"Сейчас 12:00.","ts":"..."}}
{"type":"compact","covers":[1,3],"summary":"Пользователь спрашивал время..."}
{"type":"model_switch","model":"glm-5.3-flash"}
```

Почему JSONL, а не один JSON: запись за O(1), без перезаписи файла; обрыв
процесса портит максимум последнюю строку (она пропускается с предупреждением);
файл читается глазами и через `grep`/`jq`. При старте события переигрываются,
и восстанавливаются активное окно, конспект и архив.

## Сжатие контекста

Бюджет: `-max-prompt-tokens` (6000) минус `-reserve-output` (1024). Перед каждым
запросом считается размер промпта; при заполнении выше 85% запускается сжатие.

1. **Усечение tool-выводов в промпте** до `-max-tool-chars` (800). Полный
   результат остаётся в логе.
2. **Скользящее окно** — последние ходы (не меньше `-min-tail-tokens`, 1200)
   остаются дословно. Граница окна всегда по сообщению `user`, поэтому пара
   `assistant` + `tool` никогда не рвётся.
3. **Rolling summary** — выпавший префикс сжимается дешёвой моделью в конспект
   до 250 слов. Конспект добавляется в начало system-сообщения. Каждая попытка
   ограничена 75 с; если модель сжатия не ответила (503, таймаут, пустой
   ответ), конспект один раз пробует построить **чат-модель** — в консоли это
   видно строкой «сжатие: qwen… не справился (…) — пробую glm…».
4. **Слияние** — при следующем сжатии старый конспект сворачивается вместе с
   новым префиксом.

Токены оцениваются как `руны / 2.7` и калибруются по реальному
`usage.prompt_tokens` каждого ответа (EMA), поэтому бюджет подстраивается под
токенизатор провайдера без внешних зависимостей.

## Архив, а не удаление

Из промпта сообщения уходят, с диска — никогда. Событие `compact` помечает
диапазон `seq`, при перезапуске эти сообщения попадают в архив. Достать их
можно командой `/recall <текст>`; при желании архив легко выгружается в
`archive.jsonl.gz` или SQLite, не меняя формат активного лога.

Если модель сжатия недоступна, конспект сначала пробует построить чат-модель.
Каждая попытка ограничена 75 с — зависшая модель не съест весь бюджет хода и
оставит время запасной. Если не смогла и она, сырые сообщения всё равно
архивируются, а в конспект пишется пометка с обеими ошибками и ссылкой на
`/recall` — диалог не теряется.

## Команды чата

`/help`, `/exit`, `/new`, `/session [id]`, `/model [id]`, `/system`, `/tools`,
`/history`, `/tokens`, `/compact`, `/recall <текст>`. `/session` без аргумента
показывает список сессий (текущая помечена `*`), `/session <id>` переключает на
другую сессию; `/model` без аргумента показывает список моделей, `/model <id>` меняет
чат-модель.

## Интерфейс

- **Ответ печатается по мере генерации** (SSE-стриминг, `stream: true` +
  `stream_options.include_usage`): дельты контента летят в консоль сразу, без
  ожидания полного ответа. Reasoning-дельты (черновик мышления reasoning-моделей)
  не печатаются — пока модель думает, крутится спиннер; первый токен ответа
  гасит его. Если эндпоинт не поддерживает стрим, агент автоматически повторяет
  запрос в обычном режиме; частично напечатанный ответ при обрыве не
  дублируется.
- Пока модель думает, под строкой `agent> ` крутится односимвольный спиннер
  `/ - \ |` (только в TTY; в `-script`-режиме — сообщение каждые 10 с, пока
  стрим молчит).
- После каждого ответа — строка статистики: модель, оценка промпта против
  бюджета, активное окно и архив, размер конспекта, вызовы API и стоимость.
  Детали — `/tokens`.
- Вызовы инструментов и **сжатие** печатаются строкой `  ↳ …`; срабатывание
  сжатия видно сразу: «сжатие контекста: сообщения seq 1..4 → архив, конспект
  ~100 ток., промпт теперь ~584 ток.», а в статистике растёт «архив N сообщ».
